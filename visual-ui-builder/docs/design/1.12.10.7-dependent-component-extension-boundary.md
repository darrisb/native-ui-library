# 1.12.10.7 — Dependent-Component Extension Boundary

> **Status:** Design note only — no implementation is introduced by this task.
> **Scope:** Architectural documentation for future change-triggered reloads between dependent components (e.g., country → state dropdowns).
> **Created:** 2026-10-29

---

## 1. Purpose

This document records the extension boundary the implementation must honor when adding dependent-component (cascading) data loading in a future milestone. It is written against the current codebase so that later work can be grafted onto the existing contracts without breaking import/export compatibility, validation, or the renderer's edit-mode/network-inert guarantees.

The concrete motivating example is a **country dropdown** whose selected value feeds the request parameters of a **state/province dropdown**. Changing the country should re-fetch the states endpoint with the new country identifier. Nothing in this document implements that behavior; it only describes the boundary so that when it is implemented, the fit is clean.

---

## 2. Current Milestone Boundary (What Exists Today)

The current data pipeline is **single-shot, mount-only, static-URL**:

```
ComponentInstance
  ├── dataSource: { type: "rest", method: "GET", url: string, ... }
  └── bindings:   [{ target: "options" | "rows", path?: string }]
```

The pipeline flows through these layers:

| Layer | Module | Responsibility |
|-------|--------|----------------|
| **Declaration** | `packages/core/src/types/data-source.ts` | Declarative `DataSource` contract (`RestDataSource` / `StaticDataSource`). Only `method: "GET"` and `loadOn: "mount"` are accepted. |
| **Validation** | `packages/core/src/validation/validate-data-source.ts` | Pure-function validation of `dataSource` + `bindings`. Rejects unsafe URLs, embedded secrets, malformed mappings. |
| **Fetch adapter** | `packages/renderer/src/data-source/rest-fetch-adapter.ts` | Browser-only `fetch` wrapper. http/https only, no credentials in URL, `Accept: application/json`, bounded timeout (10s), size cap (5 MiB). |
| **Resolution** | `packages/renderer/src/data-source/data-source-runtime.ts` | Lifecycle: `mount()` → fetch → `extractAndMapRecords` → bind. Epoch-based staleness guard. Idempotent per instance id. |
| **Binding** | `packages/renderer/src/data-source/data-binding-adapter.ts` | Target-agnostic adapter registry (`"options"` → `defaultOptionsAdapter`, `"rows"` → `defaultRowsAdapter`). |
| **Render integration** | `packages/renderer/src/dom/render-component.ts` | Creates one `DataSourceRuntime` per render tree in interactive mode; edit mode is network-inert. |

### 2.1 What Is Explicitly Out of Scope Today

The following capabilities are **not** present in the current milestone and are deferred:

- **Dynamic request parameters** — URLs are static strings declared in project JSON. There is no mechanism for a URL to reference another component's value at fetch time.
- **Auth / credentials** — No headers, tokens, cookies, or credentials of any kind. `RestDataSource` intentionally has no `headers` field. Validation rejects secret-like query parameter names.
- **Mutations** — Only `GET` is supported. `POST`, `PUT`, `PATCH`, `DELETE` are not declared.
- **Cascading / dependent fetches** — No data source references another component's state. There is no concept of "fetch this URL only after that dropdown changes."
- **Re-fetch triggers** — `loadOn: "mount"` is the only trigger. There is no `loadOn: "change"` or equivalent.

### 2.2 Key Invariants That Must Be Preserved

When dependent loading is added, the following invariants must hold:

1. **Edit-mode network inertness** — The builder canvas must never issue network requests. `DataSourceRuntime.mount` short-circuits when `mode !== "interactive"`. Any new trigger mechanism must respect this gate.
2. **No secrets in project JSON** — URLs embedding credentials are rejected at both validation and fetch time. Dynamic parameters that resolve to secrets must be blocked at validation time.
3. **Import/export compatibility** — All declarative data is plain serializable data that survives JSON round-tripping. Runtime state (`DataSourceRuntimeState`) is never serialized.
4. **Staleness safety** — The epoch counter in `DataSourceRuntime` discards late-arriving responses. Any new trigger that re-fires a request must capture a fresh epoch and invalidate prior pending responses.
5. **Target-agnostic pipeline** — Fetch → map → bind is independent of component type. The dependent-loading mechanism must not hardcode Dropdown-specific logic into the runtime.

## 3. Conceptual Model: Data Source vs. Action vs. Component State vs. Renderer

When implementing dependent loading, it is essential to keep four concepts distinct. They interact but are not interchangeable:

### 3.1 Data Source (the "what to fetch")

A `DataSource` is a **declarative description** of where a component's data comes from. It lives in `ComponentInstance.dataSource`. It is:

- **Serializable** — stored in project JSON, exported, version-controlled.
- **Passive** — it never fetches itself. A runtime (`DataSourceRuntime`) resolves it.
- **Self-contained** — today it has no references to other components or external state.

In a future milestone, a data source *may* declare that its URL or query parameters depend on another component's value. When it does, the data source itself remains declarative — it declares *which* value it depends on, not *how* to watch for changes.

### 3.2 Action (the "what to do on an event")

A `ComponentAction` is a **declarative description** of a behavior triggered by a DOM event. It lives in `ComponentInstance.actions`. Today the only action type is `navigate` (open a URL). Actions are dispatched by `ActionExecutor` in interactive mode.

Actions are distinct from data sources:

- An action **causes a side effect** (navigation, future: submit, emit).
- A data source **declares a data dependency** that the runtime resolves.
- An action fires in response to a **user DOM event** (`click`, `hover`, `focus`).
- A data source resolves in response to a **lifecycle trigger** (`mount`, future: `change`).

### 3.3 Component State (the "current values")

A `ComponentInstance` carries:

- `properties` — user-editable configuration values (e.g., a Dropdown's label, placeholder).
- Runtime state — internal to the renderer; includes the latest `DataSourceRuntimeState` per instance and any DOM-side state (e.g., the currently selected option value in a Dropdown).

The critical distinction for dependent loading is:

- **Properties** are serializable, user-edited, stored in project JSON.
- **Runtime state** (selected value, loading status, fetched records) is ephemeral and never exported.

When a country dropdown's selected value changes, that change lives in **runtime state**, not in `properties`. The state dropdown's data source, if it depends on the country value, must read from runtime state at fetch time.

### 3.4 Renderer (the "how it appears")

The renderer (`render-component.ts` and its subtree) is responsible for:

- Creating DOM elements from `ComponentInstance` declarations.
- Applying properties via `applyComponentProperties`.
- Binding action events via `bindActionEvents`.
- Mounting data sources via `DataSourceRuntime.mount`.

The renderer is **not** responsible for business logic like "when country changes, refetch states." That logic belongs in the runtime layer or a future orchestration layer. The renderer delegates to registered adapters (`DataBindingAdapter`) so that component-specific interpretation of data does not leak into the generic pipeline.

### 3.5 Boundaries Summary

| Concept | Lives in | Serializable? | Triggers |
|---------|----------|---------------|----------|
| Data source | `instance.dataSource` (core) | Yes | Lifecycle (`mount`, future: `change`) |
| Action | `instance.actions` (core) | Yes | DOM events (`click`, `hover`, `focus`) |
| Properties | `instance.properties` (core) | Yes | User edits in builder |
| Runtime state | Renderer memory only | No | Fetch resolution, user interaction |

## 4. Future Country → State Dropdown Dependency

### 4.1 Declarative Shape (Conceptual — Not Implemented)

A future `RestDataSource` *may* be extended to express that one or more query parameters depend on another component's runtime value. The current contract does not support this; the following is the conceptual shape the extension should converge on:

```ts
// CONCEPTUAL — not part of the current DataSource union
interface FutureDependentRestDataSource extends RestDataSource {
  /**
   * Declares that one or more query parameters of `url` are filled from
   * another component's runtime value. The runtime watches the referenced
   * component and re-resolves this data source when the value changes.
   *
   * The `componentId` refers to a sibling or ancestor component instance in
   * the same document tree. The `valuePath` is a runtime-state accessor (e.g.,
   * "selectedValue") — not a serializable data path.
   */
  readonly parameters?: ReadonlyArray<{
    readonly queryParam: string;
    readonly componentId: string;
    readonly valuePath: string; // runtime-state accessor
  }>;
}
```

The implementation must ensure that:

1. The `parameters` field is optional and defaults to `undefined` for backward compatibility.
2. A data source with `parameters` is still a `RestDataSource` — it shares the same `type: "GET"` contract.
3. Validation must reject references to non-existent `componentId` values.
4. The URL template must remain serializable — query parameter values are substituted at fetch time, not stored.

### 4.2 Component Value and Request Parameters

When the country dropdown's selected value changes:

1. The Dropdown's runtime state updates its `selectedValue`.
2. A change-event notification propagates to any data source that declared a dependency on that component.
3. The dependent data source (states dropdown) constructs its final URL by substituting the current `selectedValue` into the declared query parameter.
4. The runtime re-resolves the data source: fetch → extract+map → bind.
5. The states dropdown re-renders its options.

The **component value** here is the runtime-selected value of the country dropdown — a plain string or number. It is **not** a `ComponentProperty` (those are static configuration like label/placeholder). It is ephemeral runtime state maintained by the Dropdown component instance in the renderer.

The **request parameters** are the query string values appended to the REST endpoint URL at fetch time. They are derived from the component value by the runtime, not by the data source declaration itself.

### 4.3 Distinction: Data Source vs. Action for Dependent Loading

A dependent data load is **not** an action:

- An **action** responds to a user gesture and produces a side effect (navigation). It is event-driven.
- A **dependent data source** responds to a state change and produces new bound data. It is state-driven.

The `change` event on a Dropdown is conceptually similar to an action trigger (it is a DOM event), but the consequence is a data re-fetch, not navigation. Whether the implementation routes Dropdown changes through the `ActionExecutor` or through a separate `DataSourceRuntime` subscription is an implementation decision — but the declarative contract must remain: the data source declares the dependency, the runtime resolves it.

## 5. Browser-Only Security / CORS Limitations

### 5.1 Fetch Adapter Is Browser-Only

`createRestFetchAdapter` defaults to `globalThis.fetch`. The entire `DataSourceRuntime` is a browser-only concern:

- Edit mode short-circuits before any fetch, so the builder canvas never touches the network.
- Interactive mode (preview / export) requires a browser environment with `fetch`, `AbortController`, and streaming `Response.body.getReader`.
- There is no Node.js fallback. SSR / server-side rendering of data-bound components is not supported.

This is intentional. The renderer's data layer is a client-side concern; the builder's edit mode must remain network-inert.

### 5.2 CORS Constraints

Because fetches run in the browser, they are subject to standard CORS policy:

- **Same-origin endpoints** work without configuration.
- **Cross-origin endpoints** must return appropriate `Access-Control-Allow-Origin` headers, or the browser will block the response and the fetch adapter will surface a `"network"` error.
- The fetch adapter sends **only** `Accept: application/json` — no `Authorization` header, no cookies (`credentials` is omitted), no custom headers. This means:
  - **Public CORS-enabled APIs** work.
  - **Authenticated APIs** do not work and will not be supported until auth is explicitly added to the contract (a future milestone).
  - **APIs requiring custom headers** (API keys in headers, etc.) do not work today.

The `"credentials-in-url"` rejection at both validation and fetch adapter levels prevents a class of secret-exposure bugs. Embedding `?api_key=...` in the URL is blocked; future auth must go through a separate, explicit mechanism (not query parameters).

### 5.3 Error Safety

All errors from the fetch adapter carry a stable `code` and a safe `message` that never echoes the URL, response body, or backend headers. This is critical because:

- The URL may contain sensitive path segments (even if query secrets are blocked).
- The response body may contain PII or internal infrastructure details.
- Error messages may be rendered to the user in the builder or in exported output.

When dependent loading is added, the same safety contract applies: a dependent fetch that fails (e.g., the referenced component has no value yet) must surface a safe, stable error code — never the upstream URL or response body.

### 5.4 Export Behavior

Exported interactive renders (`mode: "interactive"`) carry the full declarative `dataSource` in their project JSON. At export time:

- The data source URL and any future `parameters` declarations are serialized.
- No runtime state (selected value, fetched records, loading status) is serialized.
- On the hosting page, `renderComponent` creates a `DataSourceRuntime` per tree and resolves each data source on mount.

For dependent components, this means:

- The export must serialize the dependency declaration (`componentId` + `queryParam` + `valuePath`) so the hosting page knows to wire up the subscription.
- The runtime on the hosting page must construct the same subscription graph from the serialized declarations.
- Circular dependencies (A depends on B, B depends on A) must be detected and rejected at validation time, before export.

## 6. Extension Points (Where Future Work Fits)

The following are the clean extension points for dependent-component loading. Each is designed to be additive — no existing contract needs to change shape.

### 6.1 `RestDataSource` Type

Add optional `parameters` field (or similar) to `RestDataSource` in `packages/core/src/types/data-source.ts`. The field is optional; its absence preserves current behavior. Validation in `validate-data-source.ts` gains a new branch that validates parameter references without altering existing URL/mapping/responsePath validation.

### 6.2 `DataSourceLoadOn` Type

Today: `export type DataSourceLoadOn = "mount";`

Future: `export type DataSourceLoadOn = "mount" | "change";` — but `"change"` is only meaningful for dependent data sources that declare `parameters`. A standalone `"change"` with no dependencies is a no-op at runtime and should be rejected at validation.

### 6.3 `DataSourceRuntime`

The runtime already supports per-instance staleness via the epoch counter. Dependent loading adds:

- A subscription mechanism: when component X's value changes, re-resolve data sources that declared a dependency on X.
- The subscription is wired at `mount()` time — the runtime inspects `dataSource.parameters` and subscribes to referenced components.
- On `unmount()`, all subscriptions are torn down alongside the existing abort/stale logic.

### 6.4 `DataBindingAdapter`

No changes needed. The binding adapter remains target-agnostic. The dependent-loading mechanism only changes *when* a data source is resolved; the resolved records flow through the same bind pipeline.

### 6.5 `ActionExecutor`

No changes needed for basic dependent loading. Actions remain event-driven side effects. If a future use case requires "on country change, navigate to a URL" — that is an action with a `change` trigger, which is a separate extension (action trigger types, not covered here).

### 6.6 `render-component.ts`

Minimal changes. The renderer already creates one `DataSourceRuntime` per render tree. If dependent subscriptions need cross-instance coordination, the runtime handles it internally; the renderer just calls `runtime.mount()` per instance as it already does.

## 7. Explicitly Deferred (Not This Milestone)

The following are documented as future work. They are **not** implemented and **not** implied by this design note:

| Capability | Why Deferred |
|-----------|--------------|
| Dynamic URL / query parameters | Requires runtime subscription graph; needs a `parameters` field on `RestDataSource` |
| Auth / credentials / headers | Security boundary — no secrets in project JSON; needs a separate auth mechanism |
| Mutations (`POST`, `PUT`, etc.) | `method: "GET"` only; mutation support requires new `DataSourceMethod` members and action semantics |
| Cascading / multi-level dependencies | Foundation is single-level dependency; multi-level chains build on the same mechanism |
| Server-side data resolution | Browser-only; SSR not supported |
| `change` action triggers | Actions are click/hover/focus today; change-triggered actions are a separate extension |
| Optimistic updates / write-back | No mutation support; write-back is a future layer |
